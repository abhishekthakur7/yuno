## Blocking findings

### 1. Title-variation and non-prediction helper copy is not shipped anywhere
- What is missing: The approved `role-competency-copy-v1` title-variation/non-prediction sentence and the per-level competency descriptions are absent from onboarding, Settings, and Interview Prep. Only a paraphrased no-beginner note survives in onboarding, and it is untested against exact wording other than the paraphrase itself.
- Owning ticket: IDK-104 (onboarding), IDK-105 (Settings/goal editor), IDK-301 (Interview Prep role/level controls) — all listed in IDK-004 §6 as the required activation evidence for `role-competency-copy-v1`.
- Evidence of absence: `src/selected/core/CorePages.tsx:359-370` and `:796`, `src/selected/operations/OperationalPages.tsx:366` — grep for `Titles vary`, `not necessarily your current title`, `predict hiring`, and the exact per-level descriptions from IDK-004 §2 across `src/selected/**/*.tsx` returns zero matches outside the decision document itself.
- What would clear it: Ship the exact IDK-004 §2 heading, audience note, title-variation helper, per-level descriptions, and target-capability helper text in onboarding, Settings, and Interview Prep, programmatically associated with the level/capability controls, then re-inspect.

### 2. Interview Prep heading does not follow the selected level
- What is missing: A dynamic heading/eyebrow reflecting the goal's actual `target_level`; the shipped heading is a hardcoded "Senior backend" literal.
- Owning ticket: IDK-301.
- Evidence of absence: `src/selected/core/CorePages.tsx:878` — `eyebrow="Interview prep · Senior backend"` is a string literal, not derived from `workspace.currentGoal.target_level` or the bundle's `target_level`.
- What would clear it: Derive the eyebrow/heading text from the actual selected level (using the shared `role-competency-copy` registry per IDK-004 §5) and re-inspect for a non-Senior goal.

### 3. Hands-on scenario metadata does not use the IDK-009 approved scenario registry
- What is missing: The six approved IDK-009 scenario records (three initial + three paired delayed, content revision `idk009-v1-r1`) are not loaded. Shipped code synthesizes a generic scenario per topic instead, and every created row is permanently labeled `scenario_status="fixture"` / `scenario_source="fixture-pending-idk-009"`.
- Owning ticket: IDK-405, whose own ticket text (`IMPLEMENTATION_TICKETS.md:1698`) requires loading "exactly the three approved initial and three paired delayed hands-on scenario records from IDK-009... content revision `idk009-v1-r1`," despite the ticket being marked "Complete."
- Evidence of absence: `server/src/yuno/modules/hands_on/service.py:25-46` (`scenario_for`, synthesizing role/title/prompt/constraints from the topic and goal rather than a fixed registry) and `:105-118` (hardcoded `"fixture"` / `"fixture-pending-idk-009"` on every `HandsOnWork` created); `server/src/yuno/modules/hands_on/models.py:31` (`scenario_status IN ('fixture')`, no `'approved'` or similar status exists in the schema at all); zero matches for any of IDK-009's eight named scenario IDs in `server/src/yuno/modules/hands_on/`.
- What would clear it: Load the IDK-009 `assessment-scenarios-v1` registry (content revision `idk009-v1-r1`) into the hands-on scenario source, bind topics to the approved scenario IDs/role/level/constraints text, add a non-fixture `scenario_status`/`scenario_source` value for approved content, and re-inspect against a live `hands_on_work` row.

## Notes and residual risk

- Both inspected databases (`server/yuno.db`, a local dev DB, and `server/.e2e.db`, a local e2e-run DB — neither production) have zero rows in `hands_on_work`, so finding 3 above rests on the code path that would populate that table, not on a live divergent row; the absence of the approved registry in the code is nonetheless independently sufficient to fail this requirement.
- The no-beginner enum constraint (finding row 3) and the absence of any affirmative hiring/promotion prediction (row 4) are the only two of the five audit items that pass; the remaining three items (title-variation copy, IDK-405 scenario metadata, and IDK-301's level-following heading) are blocking.
- IDK-004 §6 already anticipates this gap: "Until those checks pass, the stable tier names may remain visible, but invented or unapproved competency prose must not be presented as final copy." No invented competency prose was found presented as final copy (none is shown at all), which avoids a worse violation, but the required copy is simply missing rather than substituted.
- This inspection did not evaluate assistive-technology/accessibility association because there is no helper text to associate (finding 1 supersedes that check).
