## Blocking findings

### 1. UnitOfWork is opened during a request that later fails closed-schema validation

- What is missing: IDK-008 §3/§6 states the retired `"language":"relational"` signature "returns the standard `422` validation envelope before the route/UoW." The literal "before ... UoW is opened" half of that claim is not what ships.
- Owning ticket: IDK-406
- Evidence of the gap: Empirical trace (temp DB, `create_app`, `TestClient`, `app.state.uow_factory` wrapped to count calls) shows `app.state.uow_factory()` is invoked exactly once while handling a `POST /runner/confirmations` body containing `"language":"relational"`, even though the request ultimately returns `422` and creates zero rows. This happens because `confirm_runner`'s `owner_id: Annotated[str, Depends(get_owner_id)]` resolves through `get_owner_id → Depends(get_unit_of_work)` (`dependencies.py:21-30`), and FastAPI executes dependency callables as part of the same `solve_dependencies` pass that also validates the request body — a dependency's side effect can run even when body validation ultimately fails and the route function itself is never called. The opened UoW only performs a read (`uow.owners.get_local_owner()`), producing no mutation and no `runner_confirmations`/`jobs` row — the "zero side effects" claim holds — but "before ... any unit-of-work is opened" as literally written is false for this route.
- What would clear it: Either correct the decision-doc wording to state "before the route body is used to create any record" (matching what actually ships), or reorder the route so the language/schema check runs and can 422 before `Depends(get_owner_id)` is evaluated (e.g., validate the discriminant in a pre-dependency or route decorator that runs ahead of the owner lookup).

### 2. No row-specific residual-statement copy for rows 3/4/6

- What is missing: PRD Appendix C rows 3 ("process permissions define remaining host access risk"), 4 ("local machine policy remains outside product control"), and 6 ("OS failures may require manual recovery") each specify a distinct residual statement. The shipped learner-facing UI (`HandsOnLab.tsx`, `OperationalPages.tsx`) surfaces one generic "not a sandbox or hostile-code isolation... not proof of production or AWS behavior" string everywhere a runner disclosure appears; the row-3/4/6-specific residual language does not appear anywhere in `src/`.
- Owning ticket: IDK-406
- Evidence of absence: `grep -rn "host access\|machine policy\|manual recovery" src/` finds no matches; the only runner-disclosure strings shipped are the two quoted in the findings table.
- What would clear it: Either ship the per-row residual copy at the points where it is decision-relevant (e.g., alongside the workspace-cleanup/limit-breach/cancellation UI states), or record an explicit decision that the single consolidated disclosure is intended to subsume all six rows — the latter is plausible given how narrow the runner surface is, but it is not what IDK-503's instructions currently claim is shipped, so it needs its own sign-off line rather than being inferred here.

### 3. IDK-005's platform/toolchain matrix is not enforced by shipped detection

- What is missing: IDK-005 §1 requires the Java capability item to report `incompatible`/`unsupported-platform` on any host outside the approved Ubuntu 24.04 x86_64/arm64 row, and explicitly states macOS "must not produce `supported`." §3 requires bounded `/etc/os-release` reads, `WSL_INTEROP`/container marker checks, and a JDK identity/sentinel probe before any `supported` result.
- Owning ticket: IDK-406 (already partially self-disclosed in `docs/runner/IDK-406-execution-deferral.md` §5 point 2, which states "the platform discovery IDK-005 §90 specifies is itself unimplemented — no `/etc/os-release` check and no `runner_execution_environment` attestation exist in `config.py` today").
- Evidence of absence: `grep` across `server/src` for `os-release`, `WSL_INTEROP`, `WSL_DISTRO_NAME`, `dockerenv`, `osrelease` returns zero matches. `detect_command()` (`adapters.py:37-70`) implements only command-presence and version-prefix checks. Empirically reproduced: running `detect_command("java","compile-and-test","javac","")` on this macOS/Darwin development host returns `{"state": "supported", "detail": "Configured toolchain detected at request time."}` — the exact outcome IDK-005 forbids.
- What clears the immediate risk: `policy_ready()`/`require_policy()` (`service.py:65-93`) still fail closed at the *enablement* level regardless of item state — `runner_enabled` defaults `False`, all nine `runner_*` policy fields default `None`, and there is no Settings-exposed path to flip `runner_enabled` — so no learner process starts on any platform today, macOS included. This is why the gap has not caused an incident. It remains a genuine shipped mismatch between the approved matrix and the compatibility-reporting code, independent of the (separately correct) execution-enablement fail-closed gate.
- What would clear it: Implement the platform/architecture/WSL/container detection and required-identity checks IDK-005 §3 specifies, gate `detect_command`'s `supported` result on them, and add the missing `unsupported-platform`/`platform-unverifiable` test coverage — this is explicitly listed as IDK-406's own required-evidence item 2 in IDK-005 §7 and is not yet done.

## Notes and residual risk

- The runner is disabled end-to-end today: `runner_enabled=False`, all nine dependent policy fields `None`, `server/yuno.db` and `server/.e2e.db` both show 0 rows in `runner_confirmations`/`runner_records`. No learner Java process has ever run against either inspected database. This gate is being reviewed, correctly, "against a disabled runner" as `IDK-406-execution-deferral.md` itself anticipates.
- `IDK-406-execution-deferral.md` is itself the accepted-risk record for the missing IDK-007 isolation layer (broker/cgroup/namespaces/syscall filter) and is attributed to the engineering/security owner on 2026-08-14. That acceptance is explicit and in scope; this gate does not re-litigate it, only confirms the deferral document's factual claims about what is/isn't shipped, all of which checked out under direct inspection.
- Blocking finding 3 (platform-detection gap) is low current risk because the independent enablement fail-closed gate (`policy_ready`) covers for it, but it is a real, uncorrected mismatch between an approved decision and shipped code, and it would become live risk the moment anyone (including a future automated test harness or an operator following stale documentation) sets `YUNO_RUNNER_ENABLED=true` with the other eight fields configured on a non-Ubuntu host.
- Blocking finding 1 (UoW opened before validation completes) is narrow — the opened UoW is read-only and produces no persisted row — but the decision text is written in absolute terms ("before ... any unit-of-work is opened") that the shipped dependency-resolution order does not satisfy literally.
- IDK-008's RDB-static-review wording requirement is not yet testable because no RDB hands-on content has shipped; this is recorded as "not shipped" rather than "mismatch" because there is nothing yet for the requirement to apply to. It should be re-checked at the point RDB curriculum/scenarios ship under IDK-001/002/405.
