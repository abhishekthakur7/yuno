## `825a01f`'s automatic network-enqueue path -- security/engineering assessment

`825a01f` adds an hourly background sweep, `apply_staleness_recheck()` (`app.py:306-436`), that can enqueue `retrieve_source_snapshot` jobs -- real outbound network retrieval -- with no learner action. `2b5ebc2`'s `apply_snapshot_janitor()` (`app.py:265-304`) lands beside it in the same commit pair; it is pure local DB/file cleanup (`prune_excess_snapshot_bodies`, `provenance/adapters.py`), confirmed by `grep -rn "runner\|socket\|requests\|httpx\|urllib" server/src/yuno/modules/provenance/adapters.py` returning nothing network- or runner-related, so it does not bear on this assessment further.

**Is the network-disclosure gate genuinely enforced before any enqueue?** Yes, and it is the *same* gate the HTTP route uses, not a parallel one that could drift. `apply_staleness_recheck` (`app.py:370-372`) calls `uow.provider.get_active_disclosure(owner.id, "source-retrieval", "source-network-v1")` directly; `require_disclosure` (`provider/service.py:140-154`), what `POST /sources/{source_id}/retrieve` calls (`routes/provenance.py:130-135`), calls the identical `uow.provider.get_active_disclosure(owner_id, category, disclosure_version)` with the identical two literal arguments (`provider/service.py:146-148`). The only difference is response shape: the HTTP route raises `PreconditionFailedError` when disclosure is `None` (there is a request to reject); the sweep returns silently (there is no request to reject, and enqueueing nothing is the correct behavior for "no implicit page-load network access," `provenance/service.py:1`). I verified this empirically, not just by reading: `uv run pytest tests/integration/test_provenance_staleness_recheck.py -q` -> **12 passed**, including `test_wiring_without_disclosure_enqueues_nothing` (asserts zero rows in both `jobs` and `source_retrieval_commands` when no disclosure is on record) and `test_wiring_with_disclosure_one_sweep_enqueues_one_job` (asserts exactly one job when a disclosure exists and a source is due). The test helper `_sweep_once` (`test_provenance_staleness_recheck.py:454-497`) is a line-for-line mirror of the production closure I read directly in `app.py` -- I compared both side by side rather than trusting the test file's docstring claim of equivalence.

**Does a failure classify safely?** Yes, following the exact idiom `apply_retention`/`apply_snapshot_janitor` already use, and isolated from both: its own `try`/`except`, its own `app.state.staleness_recheck_failure_classification` (never touching `retention_failure_classification` or `snapshot_janitor_failure_classification`), its own `log_event` pair (`staleness_recheck.cycle.skipped/failed/completed`). Two failure paths are distinguished: `PendingJobCapError` (`app.py:409-418`) classifies as `"pending-job-cap-reached"`; any other exception (`app.py:419-430`) classifies as `"staleness-recheck-failed"`. Both are caught by a bare `except Exception` (`# noqa: BLE001`) with the classification visibly recorded, matching the sibling functions' pattern (`app.py:265-304`'s `apply_snapshot_janitor`, `app.py:271-274` original-round-3-verified retention pattern). I confirmed the cap-error path specifically rolls back cleanly: `except PendingJobCapError` sits outside the `with uow_factory() as uow:` block (`app.py:369-408` is the `with`; `409` is the `except`), so a cap hit mid-loop lets the context manager roll back the transaction before the exception propagates -- nothing partially reserved that tick is committed, and `sources_due_for_recheck` re-selects every still-due source fresh next cycle (docstring claim at `app.py:355-364`, consistent with how `reserve_source_retrieval`'s idempotency key is a function of the *current* newest snapshot, which does not advance without a commit).

**Does the new automatic path interact with the runner's disabled posture, or the dispatcher's lanes/caps, in any way that weakens a stated control?**
- **Lane separation is real and hard-coded, not inferred.** `retrieve_source_snapshot` is enqueued with `lane=JobLane.BACKGROUND` explicitly (`app.py:402`, and identically at `routes/provenance.py:146`); `java_runner` is enqueued with `lane=JobLane.INTERACTIVE` explicitly (`app.py:1018`, and identically at `routes/runner.py:272`). Neither kind appears in `_INTERACTIVE_KINDS` (`jobs_events/service.py:49-57`), so this is not relying on the fallback inference at `jobs_events/service.py:225-229` (`lane = request.lane or (...)`) -- the explicit `lane=` argument always wins. The two lanes get separate named worker threads (`jobs-interactive`/`jobs-background`, `jobs_events/service.py:138-144`).
- **The pending-job cap is shared and global, but this is pre-existing, approved, and currently inert for the runner.** `DurableJobDispatcher.reserve()` checks `repo.pending_count(request.owner_id) >= pending_cap` (`jobs_events/service.py:248-249`); `pending_count` (`jobs_events/repository.py:141-152`) counts every `queued`/`running` job for the owner **across both lanes**, not per-lane. `pending_job_cap` defaults to a fixed `Literal[100]` (`config.py:48`), independently approved as policy by `docs/decisions/IDK-010-data-lifecycle-policy.md:57` ("Policy version 1.0 now independently approves ... `pending_job_cap = 100`"), with no per-lane isolation claimed anywhere in that document or in IDK-005/007/008. So this is not a control `825a01f` weakens -- the shared global cap already existed and already applied to `export_data`/`rebuild_index`/`delete_goal`/etc. on the BACKGROUND lane before this round. What is new is one more BACKGROUND-lane producer.
- **The interaction is inert today because `java_runner` cannot currently be enqueued at all.** `start_runner` (`routes/runner.py:146-154`) calls `require_policy(settings)` (`routes/runner.py:154`) as its first line, before touching the confirmation, before constructing any `JobRequest`. `require_policy` (`runner/service.py:89-93`) raises `UnavailableError` whenever `policy_ready(settings)` is `False` -- which it is (see "Runner disabled state" below). So today, no code path can create a `java_runner` job for the staleness sweep's BACKGROUND-lane traffic to compete against; the cap-sharing concern is real in principle but has no live target while the runner stays disabled.
- **Bound on how much BACKGROUND traffic the sweep can actually generate.** `sources_due_for_recheck` only selects `AVAILABLE` sources past the 180-day cadence (`provenance/service.py:56-113`, cadence constant `_STALENESS_RECHECK_CADENCE = timedelta(days=180)` at `provenance/service.py:45`); a per-owner registry realistically stays well under the 100-job cap for an hourly sweep. `test_repeated_failures_are_retryable_until_unavailable_then_excluded` (`test_provenance_staleness_recheck.py:365-420`, ran directly, passed) empirically proves the retry-storm concern is self-limiting: a source that fails its way to `SourceAvailability.UNAVAILABLE` (IDK-003 §8's 3-attempt/72-hour rule) is excluded from the very next `sources_due_for_recheck` selection, confirmed via `assert source_id not in _due_ids(...)` after the third failure.
- **Deduplication prevents pile-up across hourly ticks.** `test_wiring_two_consecutive_sweeps_enqueue_one_job_total` (ran directly, passed) proves two sweeps against an unchanged source collapse into one job, via `dispatcher.reserve`'s idempotency-key/active-dedupe-key checks (`jobs_events/service.py:232-247`) plus `reserve_source_retrieval`'s own UNIQUE `source_retrieval_commands` idempotency record.

**Verdict on the new automatic path: sound.** The disclosure gate is the real one, not a look-alike; failure classification is isolated and does not mask or get masked by retention/janitor failures; lane separation from the runner is explicit and structural; the one theoretical concern (a shared global pending-job cap) is a pre-existing, approved property of the dispatcher that this round did not introduce and that currently has no live interaction with the runner because the runner cannot enqueue anything while disabled. Nothing here weakens a stated control.

**Interaction with B23 (the thread-name-filtered flaky test), checked with particular care since this sweep adds work to the same background lane those threads serve:** `apply_staleness_recheck`/`apply_snapshot_janitor` are called synchronously, once, at process startup (`app.py:1049`, `apply_retention()`, itself calling both at `app.py:472-473`) -- **after** `dispatcher.start()` (`app.py:1045`) but **before** the lifespan yields control back to whatever booted the app. `test_runner.py`'s `client`/`_enabled_app` fixtures build a fresh `TestClient(app)` per test (`conftest.py:127-134`, entering the ASGI lifespan on `__enter__`), so this one synchronous startup call completes in full *before* the flaky test's own body runs and attaches its SQL listeners (`test_runner.py:369-371`, after the `client` fixture is already yielding). The startup call therefore cannot itself pollute the listener capture. Whether the *ongoing* `jobs-background` poll loop that follows could enqueue extra noise depends on `sources_due_for_recheck` finding something to select; it does not, for this test's fixture: `migrated_database_url` is a fresh per-test migrated DB (`conftest.py:53-60`) with zero `sources` rows and zero accepted disclosures, so `apply_staleness_recheck`'s one startup pass enqueues nothing, and the recurring hourly loop (`periodically_apply_retention`, `app.py:498-501`, `RETENTION_INTERVAL_SECONDS=3600` at `app.py:160`) cannot fire again within a multi-second test. The `jobs-background` thread's continuous 0.1s poll (`jobs_events/service.py:434,438`) -- the actual root cause round 3 diagnosed and fixed by thread-name filtering -- is unchanged in volume or nature by this round's commits for this specific test. I did not rely on this reasoning alone; I re-ran the actual test repeatedly (below).
