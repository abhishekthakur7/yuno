## Independent end-to-end proof (janitor)

`test_provenance_snapshot_janitor.py`'s 7 tests prove the DB-side behavior (pointer-row deletion, one `file_cleanup_intents` row per pruned body, `source_snapshots` metadata untouched, idempotency, owner scoping) but **never call `execute_pending_cleanup`** -- unlike `test_provenance_license_purge.py:428`, which does for the sibling purge function. Per this task's "prove it, don't assume" rule, I wrote and ran an independent script (`prove_janitor_e2e.py`) against a disposable scratch DB migrated fresh to head: it seeds one owner, one source, and 21 real on-disk snapshot body files (indices 0-20, oldest to newest), calls `prune_excess_snapshot_bodies`, then calls the real `execute_pending_cleanup`.

Actual output:

```
prune_excess_snapshot_bodies returned: 1
source_snapshot_bodies count: before=21 after=20
source_snapshots metadata count (must be unchanged): before=21 after=21
file_cleanup_intents rows for this owner: [('...', 'source-snapshot', 'source-snapshot:3f8f...', '9a9b...', 'pending')]
execute_pending_cleanup result: completed=1 failed=0
final intent status: ('complete', '2026-08-15T06:50:40.735572Z')
PROOF PASSED: janitor pointer-delete + file_cleanup_intents insert is consumed end-to-end by execute_pending_cleanup; real file unlinked; source_snapshots metadata row untouched.
```

This confirms, by direct execution rather than by reading the docstring's claim: the oldest snapshot outside the newest-20 window is selected, its `source_snapshot_bodies` pointer row is deleted, a `kind='source-snapshot'` cleanup intent is written with `path_ref` equal to the exact `content_ref` value, `execute_pending_cleanup` resolves that reference against `ApprovedCleanupRoots.source` through the `source-snapshot:` scheme and physically unlinks the real file, the intent is marked `complete`, and the `source_snapshots` metadata row count never changes.
