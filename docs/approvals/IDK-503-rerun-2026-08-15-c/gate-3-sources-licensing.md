### 2. §12 item 9 janitor -- real, wired into production, and empirically verified against a scratch DB; prunes bodies, not snapshot rows

**The janitor itself.** `prune_excess_snapshot_bodies` (`provenance/adapters.py:390-533`, `_RETAINED_SNAPSHOTS_PER_SOURCE = 20` at line 390) orders a source's body-bearing snapshots newest-first, retains the newest 20 unconditionally, and among the rest deletes the `source_snapshot_bodies` pointer row (plus a `file_cleanup_intents` row for out-of-transaction unlink) for every snapshot with no live `citations.source_snapshot_id` reference -- a cited snapshot past the cutoff is never pruned.

**Production caller, confirmed by direct read of `app.py`, not by trusting the docstring.** `apply_snapshot_janitor()` (`app.py:265-304`) loops every source and calls `prune_excess_snapshot_bodies`; it is called unconditionally from `apply_retention()` (`app.py:472`), which itself runs once at process startup (`app.py:1049`) and then every `RETENTION_INTERVAL_SECONDS` (3600s = hourly, `app.py:160,1050`) for the life of the process. No feature flag or disclosure gate blocks it -- this is automated local maintenance, not an editorial act, so (correctly) no `designated_editorial_approver` grant check applies.

**The single most important judgment in this gate, verified empirically against my own scratch DB, not asserted from the docstring:**

```
sqlite3 "$DB" "DELETE FROM source_snapshots WHERE id='ss1';"
  -> Error: source_snapshots header is immutable

sqlite3 "$DB" "DELETE FROM source_snapshot_bodies WHERE snapshot_id='ss1';"
  -> succeeds (no error); SELECT count(*) FROM source_snapshot_bodies WHERE snapshot_id='ss1' -> 0
  -> SELECT id, content_hash, retrieved_at, status FROM source_snapshots WHERE id='ss1'
     -> ss1|abc123|2026-08-15T00:00:00Z|available  (metadata row survives)
```

I also confirmed *which* migration's trigger is active, since two exist under the same name: `6ee79a009c2a` (lines 525-539) originally creates `trg_source_snapshots_no_delete` with message `"source_snapshots is immutable"`; `e10d1a0c0100` (lines 1885-1896 drop, 2163-2185 recreate) drops it and recreates it with message `"source_snapshots header is immutable"`. My scratch DB's actual error text (`source_snapshots header is immutable`) matches `e10d1a0c0100`'s message, confirming that migration's version is what is live at head -- exactly as the code's docstring claims, independently reproduced here rather than taken on its word. `source_snapshot_bodies` carries only a `no_update` trigger (`.schema source_snapshot_bodies` on the scratch DB shows no `no_delete`), so the DELETE above succeeding is structural, not a gap the code failed to close.

**Does pruning bodies rather than metadata rows satisfy §6's "Retained snapshots per source: 20" row? Stated plainly: it substantially satisfies the row's stated rationale but does not implement the row as literally worded.** `docs/decisions/IDK-003-source-licensing-and-snapshot-policy.md:83` reads: "20, oldest-first pruning among snapshots with no live `citations.source_snapshot_id` reference," with rationale "Bounds disk growth from repeat retrieval without ever silently removing a citation's evidentiary basis." Read literally, "pruning ... snapshots" describes removing snapshot *rows*, and "20" reads as a cap on the surviving row count. That is not what ships: `source_snapshots` metadata rows are never deleted (structurally cannot be, per the immutability trigger `IDK-003:129`'s own §9 text already cites), so the row count is unbounded and grows forever regardless of the janitor. What the janitor bounds is the *body* storage -- the 10 MiB-capped file plus its pointer row -- which is also where essentially all the disk-growth risk the rationale names actually lives; a bare metadata row (id/hash/timestamp/status, no body) is a few dozen bytes. This reading is internally consistent with the very next row in the same §6 table, "License-revocation purge," which the document itself specifies the identical way: body purged, "the metadata row (hash, timestamps, status) is retained." Given that sibling row's precedent and the pre-existing immutability constraint §9 already assumes, pruning bodies is the only implementable reading of "pruning" for this table, and it delivers the rationale's actual goal (bounding disk growth) even though it does not deliver a literal 20-row cap on `source_snapshots`. This is a genuine, non-mechanical judgment call, recorded here rather than silently assumed either way.

**Tests, run fresh this round:** `rtk proxy uv run pytest tests/integration/test_provenance_snapshot_janitor.py -v` → **7 passed**: `test_at_or_under_the_retained_count_prunes_nothing`, `test_a_cleanup_intent_is_recorded_per_pruned_body`, `test_a_second_call_is_idempotent`, `test_source_snapshots_metadata_row_count_is_unchanged_by_pruning` (directly tests the body/metadata split above), `test_owner_scoping_leaves_another_owners_snapshots_untouched`, `test_a_cited_snapshot_outside_the_newest_20_survives`, `test_excess_uncited_snapshots_are_pruned_oldest_first`.

**Verdict: real, production-wired, and correctly limited to what the schema's own pre-existing immutability constraint permits -- substantially closes the janitor half of §12 item 9, with the literal-vs-rationale gap above recorded rather than papered over.**

### 3. §12 item 9 staleness -- the cadence leg is real, tested, and production-wired; the "crossing into unavailable" trigger is an argued reading, not a new or independently-tested mechanism

**The cadence leg.** `sources_due_for_recheck` (`provenance/service.py:56-113`) selects `AVAILABLE` sources whose newest non-`failed` snapshot is `>= 180 days` old (`_STALENESS_RECHECK_CADENCE`, line 45), or that have never had a successful snapshot at all. `withdrawn` and `unavailable` sources are excluded. Wired via `apply_staleness_recheck()` (`app.py:306-436`), called from `apply_retention()` (`app.py:473`) on the identical startup+hourly schedule as the janitor above. **§9's three detection triggers (`IDK-003:129`), assessed individually rather than accepted as a set:**

1. **180-day cadence** -- new this round, real, tested against the boundary. Closed.
2. **"Any explicit content-owner-initiated re-retrieval"** -- pre-existing `POST /sources/{source_id}/retrieve` (`routes/provenance.py:105-153`, untouched by this round's diff). Real and already covered before this round.
3. **"Immediately on crossing the §8 `unavailable` threshold"** -- **not a new mechanism; an argued reading of existing, unchanged code.** `_record_failed_retrieval` (`service.py:415-477`, confirmed unchanged in this round's diff of `service.py` -- only `sources_due_for_recheck`/`_latest_successful_snapshot`/`register_source` were added) is what flips a source to `unavailable` after 3 consecutive failures spanning 72+ hours. The code's own docstring (`service.py:88-97`) and the test file's own docstring (`test_provenance_staleness_recheck.py:6-15`) both state plainly that this trigger needed "no new code" because "the crossing itself is read here as the detection event." Stated plainly, as the brief asks: **this is a genuine interpretive stretch, not a mechanically verified equivalence.** §9's own "Detection" paragraph (`IDK-003:129`) defines detection as "a fresh retrieval whose hash differs from the most recent `source_snapshots.content_hash`" -- i.e., a successful retrieval that is then compared. The `unavailable` transition is the opposite: three *failed* attempts, no new content, no hash to compare. `test_repeated_failures_are_retryable_until_unavailable_then_excluded` (read in full, `service.py:365-420`+) proves only that `sources_due_for_recheck` stops selecting a source once it crosses to `unavailable` -- i.e., that no *further* retrieval is attempted -- which is consistent with, but does not independently establish, the claim that the crossing itself constitutes "detection" in §9's sense. No new signal, log event, or field distinguishes an `unavailable` transition reached via this route from the one that already existed before any staleness work shipped. This is a defensible reading (repeatedly attempting a retrieval against a source that just proved unreachable would itself be the retry storm the code elsewhere works hard to avoid), but it is an argument, not a built mechanism, and is recorded here as such rather than accepted at face value.

**A residual verification gap, worth naming plainly.** `test_provenance_staleness_recheck.py`'s own docstring (lines 24-45) states that its `test_wiring_*` cases call `_sweep_once`, "a small helper that mirrors `apply_staleness_recheck`'s body," rather than booting a real `create_app()`/`TestClient` -- and states outright that "no test in this repo drives `apply_retention`/`apply_snapshot_janitor` through a live app either." The tests validate the pure selection/pruning functions and a hand-authored replica of the closures' call shape, not the closures.

**Verdict: cadence leg closed and well-tested; the crossing-threshold trigger is argued rather than newly built or independently tested, and the app.py wiring itself (for both the janitor and the staleness sweep) has no live-boot test coverage, only direct code reading. Recorded as a residual note below, not a new blocking finding, since the underlying claim (both closures are called unconditionally at startup and hourly) is independently verifiable by direct code read and was so verified.**
