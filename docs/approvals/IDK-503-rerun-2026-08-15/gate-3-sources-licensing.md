### 4. B7 -- availability write path: partially closed, with a newly-found production-reachability gap

**Migration and constraints (`4cb74877e4ba`), verified against a scratch DB migrated to head** (see Finding 0 for why `server/yuno.db` itself could not be used):

- `ck_sources_withdrawal_reason_required_iff_withdrawn`: tested both directions with raw INSERTs. `availability_status='withdrawn', withdrawal_reason=NULL` → `CHECK constraint failed`. `availability_status='available', withdrawal_reason='license-revoked'` → `CHECK constraint failed`. `availability_status='withdrawn', withdrawal_reason='license-revoked'` → succeeds. The biconditional is enforced in both directions, not just one.
- `ck_sources_license_status_valid`: `license_status='fixture-approved'` (the old, forbidden test value) → `CHECK constraint failed`, confirming the closed vocabulary now genuinely excludes it at the DB level, not just by convention. (Confirmed separately: `fixture-approved` no longer appears anywhere in `server/tests/integration/test_generated_content_api.py`; its fixture now uses `approved-open-license`, because the CHECK forces it to.)
- Both `sources` triggers survived the batch rebuild: `DELETE FROM sources WHERE id='s3'` → `sources are retained`; re-`INSERT`ing the same `id` → `source replacement is not permitted`. Both raised exactly as `trg_sources_no_delete`/`trg_sources_no_insert_replace` specify.
- `update_source` (`repository.py:62-84`) exists and is the sole write primitive touching `availability_status`/`withdrawal_reason`/`superseded_by_source_id`; it is an UPDATE gated on `(owner_id, id)` returning `None` on no match rather than raising.

**3-failure/72h rule (`service.py:_record_failed_retrieval`, `_consecutive_failure_streak`, `_spans_failure_window`):** read in full. Both conditions (`len(streak) >= 3 and _spans_failure_window(streak)`) are required together, confirmed by reading the `and` in `service.py:244-246`. A success breaks the streak by construction (`_consecutive_failure_streak` stops at the first non-`failed` snapshot in newest-first order), which is how reset-on-success happens without a separate counter column. A `withdrawn` source can never reach this path: `run_source_retrieval_job` refuses it up front (`ConflictError` at `service.py:94-95`) before any failure/success is ever recorded.

Ran the named clearance test directly: `pytest tests/integration/test_provenance_availability_transitions.py -v` → **7 passed**, including `test_three_failures_spanning_at_least_72h_transitions_to_unavailable` (boundary case, exactly 72h) and `test_three_failures_spanning_under_72h_stays_available`, `test_two_failures_still_available`, `test_success_between_failures_resets_the_streak`, `test_unavailable_then_success_returns_to_available`, `test_withdrawn_source_is_never_transitioned_by_this_job`.

**Production reachability of the automatic path -- confirmed real.** `run_source_retrieval_job` is wired into `server/src/yuno/api/app.py:773` under the `"retrieve_source_snapshot"` job kind, which `POST /sources/{id}/retrieve` (`routes/provenance.py:105-153`) dispatches to via the real job lane (`JobLane.BACKGROUND`), behind the existing `require_disclosure(..., category="source-retrieval")` gate. A learner-triggered (or scheduled) retrieval that fails three times spanning ≥72h genuinely transitions a real source to `unavailable` in production, not just in a test harness.

**License-revocation purge -- primitive verified correct, but has NO production caller.** `purge_license_revoked_snapshot_bodies` (`adapters.py:292-383`) deletes only `source_snapshot_bodies` rows (the pointer to the persisted file) and schedules the actual file unlink via a `file_cleanup_intents` row -- `source_snapshots` itself is untouched (protected by its own `no_update`/`no_insert_replace`/`no_delete` triggers from an earlier migration, confirmed by grep), so metadata (`content_hash`/`retrieved_at`/`status`) is genuinely retained. `claims`/`citations` are never referenced by this function at all -- untouched by construction, not merely by absence of a bug. It is called from exactly one place in `service.py:withdraw_source`, gated correctly to `reason in (LICENSE_REVOKED, LICENSE_CHANGED_INCOMPATIBLE)` only (verified by reading the `if` at `service.py:188-194`; the other three reasons never reach it). `pytest tests/integration/test_provenance_withdrawal.py tests/integration/test_provenance_license_purge.py tests/integration/test_provenance_source_updates.py -v` → **26 passed**, covering both purge-triggering reasons, both non-purge reasons, idempotency of a second purge call, and that unrelated sources' bodies/claims/citations are untouched.

However: **`withdraw_source` -- and therefore the purge it gates -- has zero production callers.** `grep -rn "withdraw_source" server/src server/tests` shows every reference is in `service.py` (the definition) or `test_provenance_withdrawal.py`. `routes/provenance.py` (read in full) exposes `GET /sources`, `GET /sources/{id}`, `GET /sources/{id}/snapshots`, `POST /sources/{id}/retrieve`, `GET /claims/{id}`, and `GET /artifacts/{id}/provenance` -- no route calls `withdraw_source`. No other route file, script, or CLI entry point does either (`grep -rln "withdraw" server/src/yuno --include="*.py"` outside tests returns only the migrations and the `provenance` module's own internals). §8 requires `withdrawn` to be "entered only by explicit editorial action" -- but there is currently no action a running instance of this product can take to perform that entry. The write primitive, the state machine, and the purge are all real and independently correct; the door to invoke them in production does not exist. This is a materially different, more precise finding than the prior round's "no code path can write `availability_status` at all" -- a code path now exists, but only the automatic (job-driven) half of it is reachable from outside a test.

**Anchoring/window ambiguity, recorded as the decision leaves it:** `IDK-003` §8/§10 fix the *threshold* (3 attempts, ≥72h) but not where the 72-hour window is anchored or what counts as a "failed attempt." The implementation's choice, read directly from the code and its own comment (`service.py:31-38`): a failed attempt is any exception from `adapter.retrieve()` or a subsequent `_validate_retrieval_result` failure, recorded as a `source_snapshots` row with `status='failed'`; the window is measured earliest-to-latest across the current unbroken run of such rows (`_spans_failure_window`, comparing `streak[0].retrieved_at` to `streak[-1].retrieved_at`), not a fixed rolling window and not anchored to first-failure-plus-72h. This is a defensible literal reading, consistent with the comment's own framing, but it is an implementation choice the decision does not settle -- recorded as such, not as compliance with an explicit rule that does not exist.

**Behavior change -- failed snapshots are now visible via the read API.** `_record_failed_retrieval` persists a real `source_snapshots` row (`status='failed'`, `content_ref=f"source-retrieval:failed:{id}"`, a placeholder scheme that cannot collide with `remove_unreferenced_snapshots`' `source-snapshot:`-prefixed matching). `list_source_snapshots` (service) and `GET /sources/{id}/snapshots` (`routes/provenance.py:94-102`, `_source_snapshot`) apply no filter on `status` -- every failed attempt is returned alongside successful ones, and `SourceSnapshotResponse.status: str` (contracts.py:1154) is unconstrained, so `'failed'` passes straight through. Assessed against the decision: `source_snapshots.status`'s vocabulary (`available`, `unavailable`, `withdrawn`, `failed`) is explicitly "unchanged... not altered by this policy" (`IDK-003:175`), and IDK-003 nowhere states failed-attempt rows must be hidden from this endpoint -- so this is consistent with what's written, not a violation. But it is a real, previously-nonexistent behavior change worth a caller's attention: any UI or API consumer of `GET /sources/{id}/snapshots` that assumed every row represents a retrievable snapshot (e.g. to build a snapshot picker) will now also see failure-log entries with a synthetic, non-dereferenceable `content_ref`. Nothing in the current frontend renders this list directly (only the `snapshotsById` join inside `useArtifactProvenance`, which only looks up specific `source_snapshot_id`s and would simply never look up a failed row's id since no citation points at one), so no live UI is affected today, but a future consumer would need to filter `status='failed'` itself.

**Verdict: partially closed.** The migration, the write primitive, the automatic transition, and the purge primitive are all real, correct, and (for the automatic path only) production-reachable, verified adversarially against both a scratch DB and the real integration test suite (33 tests total across the four files, all passing). The explicit-withdrawal half of §8's state machine -- and consequently the purge, which only that half can trigger -- is unreachable outside a test today. This is closer to done than the prior round's "no code path exists at all," but it is not "closed": a designated editorial approver reading this gate cannot today actually withdraw a source through the product. **This zero-production-caller gap is carried forward as its own standalone item, Blocking finding 4 below, not merely as a remark within this B7 discussion** -- it is a distinct defect from B7's migration/CHECK/automatic-transition work, which is otherwise sound, and should not be lost inside this section's prose.
