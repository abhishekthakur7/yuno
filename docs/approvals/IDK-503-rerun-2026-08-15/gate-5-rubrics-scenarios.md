## Blocking findings

### 1. No approved rubric manifests shipped (B11 — still open)

- What is missing: `rubrics`/`rubric_dimensions` rows for `hands-on-rubric-v1`, `practice-rubric-v1`, `mock-rubric-v1` with `status = 'approved'` and IDK-009 §6's six stable dimensions, correctly marking the first two critical.
- Owning ticket: IDK-204 (rubric registry loading/version-gating) — marked "Status: Complete" in `IMPLEMENTATION_TICKETS.md:1018`, which is not consistent with rubric content being entirely absent from every inspected database and the whole repository.
- Evidence of absence: migrated scratch DB (head `be4d11f03666`) and both `server/yuno.db`/`server/.e2e.db` all show 0 rows in `rubrics` and `rubric_dimensions`; repo-wide `rg` for the three rubric IDs returns zero hits outside the decision document; four of the six stable-dimension IDs appear nowhere in shipped code at all, and the two that do appear are hardcoded as a criticality lookup set and test-fixture labels, not as content shipped through a manifest loader.
- What would clear it: IDK-204 ships a migration/seed or boot-time loader that inserts the three `status='approved'` rubric headers and their six-dimension sets matching IDK-009 §6 verbatim (names, guidance text, critical flag per dimension), then this gate re-inspects the live rows in a migrated database.

### 2. Twelve approved scenario records are still unauthored; schema now accepts them but holds none (B12 — schema half newly closed, content half still open)

- What is missing: the twelve `scenario_id` records from IDK-009 §4-§5 (`mid-order-idempotency-initial-v1` … `staff-multiregion-evolution-mock-v1`), content revision `idk009-v1-r1`, persisted as real rows with `scenario_status='approved'`.
- Owning tickets: IDK-405 (hands-on, initial+delayed), IDK-302 (Practice), IDK-303 (Mock) — all three marked "Status: Complete" in `IMPLEMENTATION_TICKETS.md` (lines 1311, 1367, 1683), which is not consistent with zero scenario content existing anywhere in the tree.
- Evidence of absence: per-ID repo-wide `rg` for all twelve exact scenario IDs finds them only in `docs/decisions/IDK-009-assessment-and-derived-state.md`, `docs/decisions/IDK-001-mvp-curriculum-spine.md`, and prior/current gate-5 approval review prose — never in `server/`, `src/`, `tests/`, or any migration/seed. `idk009-v1-r1` (the content revision) does not appear outside the decision doc. What *is* newly true, and should not be conflated with content: `92f2a85` genuinely widens the schema (`server/src/yuno/migrations/versions/be4d11f03666_hands_on_scenario_status_and_id.py`, verified against a migrated scratch DB) to admit `scenario_status='approved'` and a `scenario_id` column, and the API contract/generated client types were regenerated to match (`server/openapi.json:3594-3616`, `src/shared/api/schema.d.ts:3025,3032`) — that commit is explicit in its own message and docstring that this is "schema only," and that framing checks out.
- What would clear it: IDK-405/IDK-302/IDK-303 author and load the twelve approved scenario records verbatim from IDK-009 §5 with `scenario_status='approved'` and correct `scenario_id`s, and this gate confirms the persisted rows against IDK-009 §5's normative text field-by-field.

### 3. Persisted classification literal remains `likely-known`, not IDK-009's `likely_known` (unchanged; recorded per this gate's instructions, not elevated to a numbered finding by itself)

- What is at stake: IDK-009 §2 states, in the same sentence as the closed classification vocabulary itself: "The only persisted classification values are `likely_known`, `partial`, `unverified`, and `new`." Every shipped occurrence uses a hyphen, not an underscore.
- Blast radius if renamed unilaterally: three migration files carry the hyphenated string inside `CHECK` constraints on live columns (`6834679f0af4_learner_roadmap_overlays.py:40,127,339`; `e205f6a2c4d1_derived_progress.py:34`; `e10d1a0c0100_policy_1_0_body_separation_and_retention.py:575-587`) — an in-place rename would require a data migration across every row in every table those CHECKs guard (`roadmap` overlays and classification columns, the fixture-derived-progress memo columns), not just an enum edit. It also touches two domain `StrEnum`s (`evidence_evaluation/domain.py:12,48`, `roadmap/domain.py:59`), a bare string literal (`diagnostics/service.py:303`), three generated TypeScript union types consumed by the frontend (`schema.d.ts:3461,3847,4495`), and two learner-facing `<select>` controls whose `value` attribute is the literal string sent back to the API (`CorePages.tsx:409,460`) — a rename that missed any one of these would desynchronize a CHECK constraint, a domain enum, or a UI control from the rest, producing either silent constraint violations or an accepted-but-meaningless value depending on which layer lagged.
- This inspection does **not** recommend a unilateral rename. Per this gate's brief: record every location so the approver can see the full blast radius, and let the approver decide whether IDK-009's exact literal is a hard requirement worth a coordinated multi-table migration, or whether the decision text should instead be revised to accept the shipped spelling.
