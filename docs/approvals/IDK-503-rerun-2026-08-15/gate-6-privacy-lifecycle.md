## Notes and residual risk

- **Scope of this re-run.** This document supersedes nothing; it is an independent re-inspection per the ticket's instruction. Every citation above was re-derived against the current tree (commit range up to and including `bf664e2`, `92f2a85`, `2621d29`) rather than copied from `docs/approvals/IDK-503/gate-6-privacy-lifecycle.md`, which was read only to identify what the previous round covered.
- **Drift note 1 (carried forward, still outstanding).** `018ecd8` ("narrow the runner to Java only under approved IDK-005/IDK-008") performs an irreversible, migration-driven bulk deletion of `language='relational'` runner confirmations/records and their exclusively owned inputs/bodies/output chunks, plus the `kind='java_runner'` jobs referencing them — outside the goal-deletion transaction and outside any IDK-010 §6/§14.2 expiry schedule. IDK-010 policy 1.0 names no category for an "obsolete-runner-language migration purge." This does not contradict any approved size/retention/export/delete/logging value (none governs it), but it remains a data-lifecycle event the current policy text does not explicitly cover. No document has named this category since the prior round. Recommend the product/privacy owner note this as an accepted category during attestation.
- **New this round — not a second drift note, but flag the cross-document dependency.** The license-revocation purge (`bf664e2`) is correctly implemented and, unlike the item above, *is* named — but in `docs/decisions/IDK-003-source-licensing-and-snapshot-policy.md` §6, not in IDK-010. IDK-003 explicitly disclaims reopening any IDK-010 category and IDK-010 explicitly never mentions `sources`/`source_snapshots`, so there is no conflict between the two documents — but a reviewer checking only IDK-010 (this gate's decision-of-record) will not find this category named there. Worth recording so a future audit does not mistake "not in IDK-010" for "not approved anywhere."
- **Stale status text inside IDK-003 itself (observation, not a gate-6 finding).** `docs/decisions/IDK-003-source-licensing-and-snapshot-policy.md` §6 still reads "Not implemented — no purge-by-license-event path exists" for the License-revocation purge row, and §12 item 6 still describes the automatic-`unavailable` transition as not yet built. Both are now implemented by `bf664e2`. This is an IDK-003 documentation-freshness issue, not an IDK-010/gate-6 lifecycle defect, and is out of this gate's decision-of-record scope — noted only so it isn't mistaken for a code gap.
- **Residual risk — unbounded `source_snapshots` growth now has a second write path.** Failed retrievals append immutable, un-expirable `source_snapshots` rows (finding 10). IDK-003 already acknowledges no pruning janitor exists for this table even for successful snapshots ("Retained snapshots per source: 20 ... Not implemented — no janitor exists"). No approved numeric limit is violated because none exists for this table under either IDK-010 or IDK-003's implemented state, but the rationale IDK-003 gives for exempting this table from expiry ("curated, low-cardinality") is weaker now that every failed retrieval attempt, not just curated additions, writes a row. Recommend flagging for the product/privacy owner's attention even though it is not a blocking finding for this gate.

Neither file was written to during this inspection (read-only `SELECT` against `sqlite_master`/`alembic_version` only). Any reviewer intending to use either file as a representative dataset for §10's review must first migrate it (`uv run alembic upgrade head`) or use a freshly seeded database — as-is, neither database can exercise `bf664e2`'s new columns or purge path at all.
